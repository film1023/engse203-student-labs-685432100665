## 1. ทำไมโปรเจกต์นี้เลือก SQLite แทน MongoDB

ข้อมูลของเรามีโครงชัดเจนและคงที่ ทุกคำร้องมี field ชุดเดียวกัน และมีความสัมพันธ์ระหว่างตารางจริง คือผู้ใช้ 1 คนแจ้งได้หลายคำร้อง ฐานข้อมูลเชิงสัมพันธ์จึงเหมาะ เพราะเก็บชื่อผู้ใช้ไว้ที่เดียวแล้ว `JOIN` เอา และบังคับความถูกต้องได้ที่ระดับฐานข้อมูลด้วย Foreign Key, CHECK และ UNIQUE ซึ่ง MongoDB ไม่ได้บังคับให้โดยตรง นอกจากนี้ SQLite เป็นไฟล์เดียว ไม่ต้องติดตั้งหรือดูแล server แยก มาพร้อม Node 22 และขนาดข้อมูลของระบบนี้เล็ก จึงไม่จำเป็นต้องใช้ฐานข้อมูลที่ขยายข้ามหลายเครื่องแบบ MongoDB

## 2. ถ้าวันหนึ่งต้องเปลี่ยนไป MongoDB จะกระทบชั้นไหนบ้าง

กระทบ **service และ controller** ส่วน route และ React ไม่กระทบ ที่ผ่านมา 4 ครั้งเราแก้แค่ service ได้เพราะแหล่งข้อมูลทุกตัว (array, localStorage, API ฝั่ง client, SQLite) ตอบกลับทันทีแบบ sync หรือถูกห่อไว้ในชั้นเดียวแล้ว แต่ MongoDB อยู่คนละเครื่อง driver ของมันคืน **Promise** ทุกคำสั่ง ฟังก์ชันใน service จึงต้องเป็น `async` และ controller ที่เรียก `service.findAll()` อยู่ตอนนี้จะได้ Promise แทนข้อมูล ต้องเติม `async/await` ทุกตัว นอกจากนั้น service ต้องเขียน query ใหม่เป็นรูปแบบของ MongoDB (เช่น `find`, `$lookup` แทน `JOIN`) และ schema.sql/constraint ต้องย้ายไปตรวจในโค้ดแทน แต่รูปแบบ JSON ที่ API ส่งออกยังเหมือนเดิม React จึงไม่ต้องแก้

## 3. async จำเป็นเมื่อไร ไม่จำเป็นเมื่อไร

async จำเป็นเมื่อการรอผลใช้เวลาที่เราควบคุมไม่ได้ โดยเฉพาะเมื่อข้อมูลอยู่ **คนละเครื่อง** ต้องรอข้ามเครือข่าย เช่น MongoDB Atlas, PostgreSQL บน cloud หรือการเรียก API อื่น ถ้ารอแบบ sync เซิร์ฟเวอร์ Node ที่มี thread หลักเดียวจะหยุดตอบคำขอของผู้ใช้คนอื่นทั้งหมดระหว่างรอ ส่วน SQLite ผ่าน `node:sqlite` อยู่ **ในเครื่องเดียวกับ API** อ่านไฟล์เล็ก ๆ ในเวลาไม่กี่มิลลิวินาที จึงใช้แบบ sync ได้โดยไม่เสียการตอบสนองที่สังเกตได้ และโค้ดอ่านง่ายกว่า แต่ถ้าข้อมูลโตมากหรือ query หนัก แม้จะอยู่ในเครื่องก็ควรพิจารณา async หรือย้ายงานหนักออกจาก thread หลัก

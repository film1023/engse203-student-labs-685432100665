## 2. ภาพรวมระบบ

ระบบรับคำร้องขอใช้บริการภายในมหาวิทยาลัย ให้นักศึกษาและบุคลากรแจ้งซ่อม ขอใช้ห้อง หรือขอบริการบัญชีผู้ใช้ผ่านเว็บได้ เจ้าหน้าที่ดูรายการคำร้องทั้งหมด ปรับสถานะการดำเนินการ และปิดงานเมื่อเสร็จสิ้น

API นี้เป็นส่วนหลังบ้าน (Express) ที่ให้ข้อมูลแก่เว็บแอป React แยกจากส่วนแสดงผล · ข้อมูลเก็บในหน่วยความจำของเซิร์ฟเวอร์ — **รีสตาร์ต API แล้วข้อมูลกลับเป็นค่าเริ่มต้นจาก `data/initialRequests.json`**

## 3. โครงสร้างข้อมูลหลัก

### Request (คำร้อง)

| Field | ชนิด | จำเป็น | ข้อจำกัด | ตัวอย่าง |
|---|---|:---:|---|---|
| `id` | string | — | เซิร์ฟเวอร์สร้างให้ · ขึ้นต้นด้วย `REQ-` | `"REQ-001"` |
| `requesterName` | string | ✓ | อย่างน้อย 2 ตัวอักษร (ไม่นับช่องว่างหัวท้าย) | `"สมชาย ใจดี"` |
| `requestType` | string | ✓ | 1 ใน 4 ค่าที่กำหนด (ดูด้านล่าง) | `"แจ้งซ่อม"` |
| `location` | string | ✓ | ห้ามว่าง | `"ห้องปฏิบัติการ 301"` |
| `details` | string | ✓ | อย่างน้อย 10 ตัวอักษร | `"เครื่องปรับอากาศไม่ทำงานตั้งแต่เช้า"` |
| `priority` | string | ✓ | `"normal"` หรือ `"urgent"` | `"urgent"` |
| `status` | string | — | เซิร์ฟเวอร์กำหนด · เริ่มต้นเป็น `"pending"` · เปลี่ยนผ่าน `PUT` | `"pending"` |

**ค่าที่ยอมรับของ `requestType`** (ตามที่ `validateRequest.js` ตรวจจริง)

`แจ้งซ่อม` · `บริการบัญชีผู้ใช้` · `ขอใช้ห้อง` · `อื่น ๆ`

> ข้อมูลตั้งต้นบางรายการมี `requestType` เป็น `ขอใช้อุปกรณ์` (เช่น REQ-003) — อ่านได้ปกติ แต่สร้างคำร้องใหม่ด้วยค่านี้จะได้ `400`

**ค่าที่ยอมรับของ `status`**

| ค่า | ความหมาย | ใครเปลี่ยนได้ |
|---|---|---|
| `pending` | รอดำเนินการ (ค่าเริ่มต้นเมื่อสร้าง) | ระบบตั้งให้อัตโนมัติ |
| `in-progress` | กำลังดำเนินการ | เจ้าหน้าที่ |
| `completed` | เสร็จสิ้น | เจ้าหน้าที่ |

| # | Method | Endpoint | ทำอะไร | สำเร็จ | ผิดพลาดที่เป็นไปได้ |
|---|---|---|---|---|---|

## 5. รายละเอียดแต่ละ Endpoint

> ทุกตัวอย่าง response ด้านล่างคัดลอกจากการยิงจริงกับ API ในเครื่อง (18/10/2026) โดยเริ่มจากข้อมูลตั้งต้น · ตัด field `stack` ที่โหมด development แนบมาออก (ดูข้อ 6)

### 5.1 `GET /api/requests` — ดูคำร้องทั้งหมด

**ทำอะไร** คืนรายการคำร้องทั้งหมด เรียงตามลำดับที่สร้าง

**Query parameters**

| ชื่อ | จำเป็น | ค่าที่ใช้ได้ | ทำอะไร |
|---|:---:|---|---|
| `status` | — | `pending` · `in-progress` · `completed` | กรองเฉพาะสถานะที่ระบุ |

**ตัวอย่างคำขอ**

```http
GET /api/requests?status=pending HTTP/1.1
Host: localhost:3001
```

**ตอบกลับเมื่อสำเร็จ — `200 OK`**

```json
[
  {
    "id": "REQ-001",
    "requesterName": "สมชาย ใจดี",
    "requestType": "แจ้งซ่อม",
    "location": "ห้องปฏิบัติการ 301",
    "details": "เครื่องปรับอากาศไม่ทำงานตั้งแต่เช้า",
    "priority": "urgent",
    "status": "pending"
  }
]
```

ถ้าไม่มีคำร้องที่ตรงเงื่อนไข จะได้ `[]` พร้อม `200` — **ไม่ใช่ `404`** · ค่า `status` ที่ไม่รู้จักก็ได้ `[]` เช่นกัน

---

**Path parameters**

| ชื่อ | ชนิด | ตัวอย่าง |
|---|---|---|
| `id` | string | `REQ-001` |

**ตอบกลับเมื่อสำเร็จ — `200 OK`**

```json
{
  "id": "REQ-001",
  "requesterName": "สมชาย ใจดี",
  "requestType": "แจ้งซ่อม",
```

**ตอบกลับเมื่อไม่พบ — `404 Not Found`**

```json
{ "error": "ไม่พบคำร้องรหัส REQ-999" }
```

### 5.3 `POST /api/requests` — สร้างคำร้องใหม่

**ทำอะไร** สร้างคำร้องใหม่ · เซิร์ฟเวอร์สร้าง `id` และตั้ง `status` เป็น `pending` ให้เอง · ถ้าส่ง `id`/`status` มาจะถูกละเลย

**Request body**

```json
{
  "requesterName": "สุภาวดี รักเรียน",
  "requestType": "ขอใช้ห้อง",
  "location": "ห้องประชุม 2",
  "details": "ขอใช้ห้องประชุมสำหรับนำเสนอโครงงาน",
  "priority": "normal"
}
```

**ตอบกลับเมื่อสำเร็จ — `201 Created`**

```json
{
  "id": "REQ-MVDCZ3Z8-A8YP",
  "requesterName": "สุภาวดี รักเรียน",
  "requestType": "ขอใช้ห้อง",
  "location": "ห้องประชุม 2",
  "details": "ขอใช้ห้องประชุมสำหรับนำเสนอโครงงาน",
  "priority": "normal",
  "status": "pending"
}
```

**ตอบกลับเมื่อข้อมูลไม่ถูกต้อง — `400 Bad Request`** (ส่ง `requesterName: "ก"`, `details: "สั้น"`)

```json
{
  "error": "ข้อมูลคำร้องไม่ถูกต้อง",
  "details": [
    "ชื่อผู้แจ้งต้องมีอย่างน้อย 2 ตัวอักษร",
    "รายละเอียดต้องมีอย่างน้อย 10 ตัวอักษร"
  ]
}
```

`details` เป็น array เสมอ แม้ผิดข้อเดียว

---

### 5.4 `PUT /api/requests/:id` — เปลี่ยนสถานะคำร้อง

**ทำอะไร** เปลี่ยน `status` ของคำร้องที่ระบุ แล้วคืนคำร้องฉบับที่อัปเดตแล้ว · แก้ได้เฉพาะ `status` — field อื่นใน body จะถูกละเลย

**Path parameters**

| ชื่อ | ชนิด | ตัวอย่าง |
|---|---|---|
| `id` | string | `REQ-001` |

**Request body**

```json
{ "status": "in-progress" }
```

**ตอบกลับเมื่อสำเร็จ — `200 OK`**

```json
{
  "id": "REQ-001",
  "requesterName": "สมชาย ใจดี",
  "requestType": "แจ้งซ่อม",
  "location": "ห้องปฏิบัติการ 301",
  "details": "เครื่องปรับอากาศไม่ทำงานตั้งแต่เช้า",
  "priority": "urgent",
  "status": "in-progress"
}
```

**ตอบกลับเมื่อสถานะไม่ถูกต้อง — `400 Bad Request`** (ส่ง `{ "status": "done" }` หรือไม่ส่ง `status`)

```json
{ "error": "สถานะต้องเป็น pending, in-progress หรือ completed" }
```

**ตอบกลับเมื่อไม่พบคำร้อง — `404 Not Found`**

```json
{ "error": "ไม่พบคำร้องรหัส REQ-999" }
```

> ลำดับการตรวจ: ตรวจค่า `status` ก่อน แล้วค่อยหาคำร้อง — ถ้าทั้ง status ผิดและไม่พบรหัส จะได้ `400`

---

### 5.5 `DELETE /api/requests/:id` — ลบคำร้อง

**ทำอะไร** ลบคำร้องที่ระบุออกจากระบบถาวร

**ตอบกลับเมื่อสำเร็จ — `204 No Content`**

ไม่มี body ส่งกลับ

**ตอบกลับเมื่อไม่พบ — `404 Not Found`**

```json
{ "error": "ไม่พบคำร้องรหัส REQ-002" }
```

- ลบแล้วยิง `GET /api/requests/REQ-002` ซ้ำ → `404` `{ "error": "ไม่พบคำร้องรหัส REQ-002" }`
- ลบรหัสเดิมซ้ำเป็นครั้งที่สอง → `404` (ข้อความเดียวกัน)

## 6. รูปแบบ Error มาตรฐาน

ทุก error ตอบเป็น JSON ที่มี field `error` เสมอ

```json
{ "error": "ข้อความที่ผู้ใช้ทั่วไปอ่านเข้าใจ" }
```

กรณี validation ของ `POST` มี `details` เป็น array เพิ่มมา

| กรณี | Status | ตัวอย่าง body (จริง) |
|---|---|---|
| ไม่พบเส้นทาง | `404` | `{ "error": "ไม่พบเส้นทาง GET /nope" }` |
| ส่ง JSON ที่รูปแบบเสีย | `400` | `{ "error": "รูปแบบ JSON ที่ส่งมาไม่ถูกต้อง" }` |
| โค้ดเซิร์ฟเวอร์ผิดพลาด | `500` | `{ "error": "เกิดข้อผิดพลาดภายในเซิร์ฟเวอร์" }` |

**โหมด development** (`NODE_ENV=development`) จะแนบ `stack` (3 บรรทัดแรก) มาด้วยเพื่อช่วยดีบัก เช่น

```json
{ "error": "ไม่พบคำร้องรหัส REQ-999", "stack": ["AppError: ไม่พบคำร้องรหัส REQ-999", "    at getRequest (…/requestController.js:15:21)", "…"] }
```

**โหมด production** (`NODE_ENV=production`) **ไม่ส่ง `stack`** และ error 5xx ตอบข้อความกลาง ๆ เสมอ (รายละเอียดจริงถูก log ฝั่งเซิร์ฟเวอร์ด้วย `console.error`) · client ไม่ควรพึ่ง field `stack`

### ตาราง Status Code ที่ใช้

| Status | ใช้เมื่อ | ฝั่งไหนผิด | ฝั่ง client ควรทำอะไร |
|---|---|---|---|
| `200` | สำเร็จ มีข้อมูลส่งกลับ | — | แสดงข้อมูล |
| `201` | สร้างสำเร็จ | — | แสดงรายการที่สร้าง (ใช้ `id` ที่ได้กลับ) |
| `204` | ลบสำเร็จ ไม่มีข้อมูลส่งกลับ | — | อัปเดตหน้าจอ ไม่ต้อง parse body |
| `400` | ข้อมูลที่ส่งมาไม่ถูกต้อง | ผู้ใช้ | แสดง `error`/`details` ให้แก้แล้วส่งใหม่ · ไม่ต้อง retry |
| `404` | ไม่พบทรัพยากรที่ขอ | ผู้ใช้ | แสดง "ไม่พบข้อมูล" · ไม่ต้อง retry |
| `500` | โค้ดเซิร์ฟเวอร์ผิดพลาด | เซิร์ฟเวอร์ | แสดง "เกิดข้อผิดพลาด ลองใหม่" · retry ได้ |

## 7. CORS

API อนุญาตให้เรียกจาก origin ที่กำหนดใน `CORS_ORIGIN` เท่านั้น (ค่าเริ่มต้น `http://localhost:5173`) — ยืนยันจากการยิงจริง:

```
GET /api/requests/REQ-003   Origin: http://localhost:5173
→ 200   Access-Control-Allow-Origin: http://localhost:5173

OPTIONS /api/requests       Origin: http://localhost:5173 · Access-Control-Request-Method: POST
→ 204   Access-Control-Allow-Origin: http://localhost:5173
```

ถ้าเรียกจาก origin อื่น เบราว์เซอร์จะบล็อกก่อนที่โค้ดจะได้เห็น response · **CORS เป็นกลไกของเบราว์เซอร์เท่านั้น** — Postman/`curl` ไม่ถูกบล็อก

บทที่ 1

จาก Week 04 มาถึงที่นี่

เวลาอ่าน ≈ 6 นาที

สัปดาห์ที่แล้วคุณสร้างระบบแจ้งคำร้องที่ทำงานได้จริง มีฟอร์มที่ตรวจข้อมูล มีการเพิ่ม กรอง และลบรายการ ทั้งหมดนั้นยังใช้ได้และจะไม่ถูกทิ้ง

สิ่งที่เปลี่ยนคือคำถามที่เราถาม Week 04 ถามว่า “component นี้ควรแสดงอะไร” ส่วน Week 05 ถามว่า “URL นี้ควรเปิดหน้าไหน และหน้านั้นควรได้ข้อมูลมาจากที่ใด”

🔵 ทายก่อนอ่านต่อ

เปิดงาน Week 04 ของคุณขึ้นมา แล้วลองตอบ 3 ข้อนี้

  1. ถ้าคุณอยากส่งลิงก์ให้เพื่อนดูคำร้อง REQ-002 โดยเฉพาะ ทำได้ไหม
  2. ถ้ากด refresh ตอนนี้ คำร้องที่เพิ่งเพิ่มจะเป็นอย่างไร
  3. ถ้าข้อมูลอยู่บนเซิร์ฟเวอร์แล้วโหลดช้า 3 วินาที ผู้ใช้จะเห็นอะไรระหว่างนั้น

ทั้งสามข้อคือโจทย์ของ Week 05 — ข้อ 1 กับ 3 แก้ในคาบนี้ ส่วนข้อ 2 แก้ในคาบหน้า

ทำไมไม่เริ่มโปรเจกต์ใหม่ให้จบ ๆ ไป

การเริ่มใหม่ง่ายกว่ามาก แต่มันหลบเลี่ยงบทเรียนที่สำคัญที่สุดของอาชีพนี้ — ในงานจริงคุณแทบไม่เคยได้เริ่มจากศูนย์ คุณจะได้ระบบที่มีคนใช้อยู่ แล้วต้องเพิ่มความสามารถโดยที่ของเดิมต้องไม่พัง

ทักษะนั้นเรียกว่า regression thinking และเป็นสิ่งที่แยกนักพัฒนามือใหม่ออกจากมืออาชีพ

ผู้เรียนหลายคนตื่นเต้นกับ routing จนลืมทดสอบว่าฟอร์มยังบันทึกได้ไหม พอถึงตอนตรวจงานถึงพบว่า feature ใหม่ทำงานสวยงามแต่ของเดิมพังไปแล้ว

ถ้าของใหม่ทำงานแต่ของเดิมหาย ถือว่างานยังไม่สำเร็จ

บทที่ 2

หน้าเดียวแต่มีหลายหน้าได้อย่างไร

เวลาอ่าน ≈ 8 นาที

เว็บสมัยก่อนทำงานตรงไปตรงมา ผู้ใช้กดลิงก์ เบราว์เซอร์ขอไฟล์ใหม่จากเซิร์ฟเวอร์ เซิร์ฟเวอร์ส่ง HTML กลับมา หน้าจอกะพริบแล้วโหลดใหม่ทั้งหน้า แบบนี้เรียกว่า Multi-Page Application

แอปที่เราสร้างเป็น Single Page Application — มีไฟล์ index.html เพียงไฟล์เดียวตั้งแต่ต้นจนจบ เมื่อผู้ใช้กดลิงก์ เบราว์เซอร์ไม่ได้ไปขอไฟล์ใหม่ แต่ JavaScript ที่ทำงานอยู่แล้วเป็นคนสลับ component ที่แสดง ให้

เครื่องหมาย # ในที่อยู่เว็บคืออะไร

ในคาบนี้เราใช้ HashRouter ซึ่งเก็บตำแหน่งของหน้าไว้หลังเครื่องหมาย # เช่น

https://username.github.io/labs/week-05/#/requests/REQ-001
└──────────── เซิร์ฟเวอร์เห็นแค่ส่วนนี้ ────────────┘└─ เบราว์เซอร์จัดการเอง ─┘

เหตุผลอยู่ที่ปลายทางของงาน — เราจะเผยแพร่บน GitHub Pages ซึ่งเป็น static hosting คือส่งไฟล์ตามที่ขอเท่านั้น ไม่มีโปรแกรมคอยตัดสินใจ

🔵 ทายก่อนอ่านต่อ

สมมติเราไม่ใช้ # แล้วผู้ใช้เปิด เว็บของเรา/requests/new ตรง ๆ แล้วกด refresh — เซิร์ฟเวอร์ที่ส่งได้แต่ไฟล์ตามชื่อ จะทำอย่างไร

เฉลย

เซิร์ฟเวอร์จะไปหาโฟลเดอร์ requests ที่มีไฟล์ new อยู่ข้างใน ซึ่งไม่มีอยู่จริง เพราะเราสร้างแค่ index.html ไฟล์เดียว ผลคือผู้ใช้จะได้หน้า 404 ของ GitHub แทนที่จะได้แอปของเรา

แต่ส่วนที่อยู่หลัง # เบราว์เซอร์ไม่ส่งไปให้เซิร์ฟเวอร์เลย เซิร์ฟเวอร์จึงเห็นแค่คำขอ index.html ตามปกติ แล้ว Router ค่อยอ่าน #/requests/new ตอนที่แอปเริ่มทำงาน

🟡 หมายเหตุ

ในระบบจริงหลายแห่งใช้ BrowserRouter ที่ URL สวยกว่าเพราะไม่มี # แต่ต้องตั้งค่าเซิร์ฟเวอร์ให้ส่ง index.html กลับมาทุกเส้นทาง เราเลือก HashRouter เพราะเหมาะกับ static hosting และตรวจสอบได้ง่ายในบริบทของวิชานี้ — ไม่ใช่เพราะมันดีกว่าเสมอไป

🔴 กับดักที่พบบ่อย

เมื่อเห็นว่า URL มี # ผู้เรียนมักเขียน path ในโค้ดแบบนี้

<Route path="#/about" element={<AboutPage />} />   ← ผิด
<Route path="about" element={<AboutPage />} />     ← ถูก

# เป็นงานของ Router ไม่ใช่งานของเรา — Router จะเติมให้เอง ถ้าเราใส่เข้าไปด้วยจะกลายเป็นการหา path ที่ชื่อว่า #/about ซึ่งไม่มีอยู่

สรุปบทที่ 2
  • SPA มี index.html ไฟล์เดียว — Router สลับ component ให้ ไม่ได้โหลดหน้าใหม่
  • ตรวจสอบได้จริงด้วย DevTools แท็บ Network
  • HashRouter เก็บเส้นทางหลัง # ทำให้ refresh บน static hosting ไม่ 404
  • ค่า path ในโค้ดไม่ต้องใส่ #

บทที่ 3

สถาปัตยกรรม 5 ชั้นและหน้าที่ของแต่ละชั้น

เวลาอ่าน ≈ 9 นาที

เมื่อแอปโตขึ้น คำถามที่จะเจอบ่อยที่สุดไม่ใช่ “เขียนโค้ดนี้อย่างไร” แต่คือ “โค้ดนี้ควรอยู่ไฟล์ไหน”

การแยกชั้นไม่ได้ทำเพื่อให้ดูเป็นระเบียบ แต่เพื่อให้แต่ละไฟล์ตอบคำถามเดียว เมื่อมีบั๊กเกิดขึ้น คุณจะรู้ทันทีว่าต้องไปดูที่ไหน

ชั้นตอบคำถามว่าไม่ควรทำ

🔵 ทายก่อนอ่านต่อ

เฉลย

บทที่ 4

Route Contract และ “ไม่พบ” สองแบบ

เวลาอ่าน ≈ 10 นาที

Route คือข้อตกลงระหว่าง URL กับสิ่งที่ผู้ใช้จะเห็น เมื่อตกลงแล้วต้องคงที่ เพราะผู้ใช้จะบันทึกลิงก์ ส่งต่อให้เพื่อน และคาดหวังว่าจะได้หน้าเดิม

4.1 Layout กับ Outlet

ทุกหน้ามีส่วนที่เหมือนกัน — แถบหัวเว็บ เมนู และท้ายเว็บ ถ้าเขียนซ้ำในทุกหน้า เวลาแก้ก็ต้องแก้ห้าที่

AppLayout คือกรอบร่วมนั้น ส่วน <Outlet /> คือช่องว่างที่ Router จะเอาหน้าปัจจุบันมาวางลงไป

4.2 Dynamic Route — เส้นทางที่มีตัวแปร

เราไม่สามารถเขียน route แยกให้คำร้องทุกใบได้ เพราะคำร้องใหม่เกิดขึ้นได้เรื่อย ๆ จึงใช้เครื่องหมาย : เพื่อบอกว่าส่วนนี้เปลี่ยนแปลงได้

<Route path="requests/:requestId" element={<RequestDetailPage />} />

// ในไฟล์ RequestDetailPage.jsx
const { requestId } = useParams();   // ได้ค่า "REQ-001"

ชื่อที่อยู่หลัง : กับชื่อที่ดึงออกมาจาก useParams() ต้องสะกดตรงกันเป๊ะ ถ้าไม่ตรงจะได้ค่า undefined โดยไม่มีข้อความเตือนใด ๆ

4.3 “ไม่พบ” สองแบบที่ต้องแยกให้ออก

🔵 ทายก่อนอ่านต่อ

#/requests/REQ-999 (ไม่มีคำร้องรหัสนี้) กับ #/xyz (ไม่มีเส้นทางนี้) — ผู้ใช้ก็ “หาไม่เจอ” เหมือนกันทั้งคู่ ทำไมเราต้องทำให้แสดงคนละแบบ

เฉลย

เพราะทั้งสองกรณีบอกผู้ใช้คนละเรื่อง และผู้ใช้ควรทำคนละอย่างต่อไป

#/requests/REQ-999 — URL ถูกต้องตามรูปแบบ ระบบเข้าใจว่าคุณต้องการดูคำร้อง แต่คำร้องรหัสนี้ไม่มีอยู่ อาจเพราะพิมพ์รหัสผิด หรือคำร้องถูกลบไปแล้ว ผู้ใช้ควรได้เห็นว่ารหัสที่หาไม่เจอคือรหัสอะไร

#/xyz — ระบบไม่รู้จักเส้นทางนี้เลย อาจเพราะลิงก์เสียหรือพิมพ์ผิด ผู้ใช้ควรได้ทางกลับไปหน้าหลัก

ลองนึกถึงร้านหนังสือ — “ไม่มีหนังสือเล่มนี้ในร้าน” ต่างจาก “ไม่มีชั้นวางชื่อนี้” คนละเรื่องกันโดยสิ้นเชิง

กรณีเกิดอะไรขึ้นผู้ใช้เห็น
#/requests/REQ-999 route ตรง แต่ไม่มีข้อมูล อยู่ในหน้า Detail เห็นข้อความ “ไม่พบคำร้อง REQ-999” และลิงก์กลับหน้าหลัก
#/xyz ไม่มี route ไหนตรงเลย หน้า NotFoundPage พร้อมลิงก์กลับหน้าหลัก
🔴 กับดักที่พบบ่อย

ผู้เรียนมักทำให้ “ไม่พบคำร้อง” กลายเป็นสถานะ error แล้วแสดงหน้าจอสีแดงพร้อมปุ่มลองใหม่

การหาข้อมูลไม่เจอไม่ใช่ความผิดพลาด ระบบทำงานถูกต้องทุกอย่าง เพียงแต่ข้อมูลนั้นไม่มี การกดลองใหม่ก็จะไม่เจออยู่ดี

สรุปบทที่ 4
  • Route คือข้อตกลงระหว่าง URL กับหน้าที่แสดง — ต้องคงที่
  • <Outlet /> คือช่องว่างใน Layout ที่ Router เอาหน้าปัจจุบันมาวาง
  • :requestId ในเส้นทาง อ่านค่าออกมาด้วย useParams() และชื่อต้องตรงกัน
  • “ไม่มีข้อมูล” กับ “ไม่มีเส้นทาง” ต้องแสดงคนละแบบ และไม่ใช่ error ทั้งคู่

บทที่ 5

Render, Event และ Effect

เวลาอ่าน ≈ 12 นาที · บทที่สำคัญที่สุด

ถ้าคุณจำอะไรจากคาบนี้ได้เพียงเรื่องเดียว ขอให้เป็นเรื่องนี้ เพราะเป็นเรื่องที่จะใช้ตลอดไปใน React และเป็นจุดที่ผู้เรียนพลาดมากที่สุด

งานในแอปหนึ่งตัวแบ่งได้เป็น 3 ชนิด ตามสิ่งที่ทำให้มันเริ่มทำงาน

5.1 ทำไม Effect ถึงเป็นชนิดพิเศษ

React มีงานเดียวคือ “รับ state เข้ามา แล้ววาดหน้าจอออกไป” ตราบใดที่งานทั้งหมดอยู่ในวงจรนี้ React จัดการได้เอง

แต่บางอย่างอยู่นอกวงจร — ไฟล์ข้อมูล เซิร์ฟเวอร์ ชื่อบนแท็บเบราว์เซอร์ ที่เก็บข้อมูลในเครื่อง สิ่งเหล่านี้ React ไม่รู้จักและควบคุมไม่ได้

useEffect คือประตูเชื่อมระหว่างโลกของ React กับโลกภายนอก ไม่ใช่ที่เก็บโค้ดที่ไม่รู้จะเอาไปไว้ไหน

🔴 กับดักที่พบบ่อยที่สุดของทั้งสัปดาห์

ผู้เรียนจำนวนมากเขียนแบบนี้

const [filtered, setFiltered] = useState([]);

useEffect(() => {
  setFiltered(requests.filter(r => r.status === statusFilter));
}, [requests, statusFilter]);   ← ทำงานได้ แต่ไม่ควรทำ

โค้ดนี้ทำงานได้จริง ซึ่งเป็นสาเหตุที่มันอันตราย ปัญหามีสามข้อ

  1. filtered คำนวณได้จาก requests กับ statusFilter ที่มีอยู่แล้ว ไม่จำเป็นต้องเก็บซ้ำ
  2. ทุกครั้งที่ตัวกรองเปลี่ยน หน้าจอจะวาด 2 รอบ — รอบแรกด้วยค่าเก่า รอบสองหลัง Effect ทำงานเสร็จ ผู้ใช้อาจเห็นข้อมูลผิดแวบหนึ่ง
  3. ข้อที่แย่ที่สุด — ตอนนี้เรามีข้อมูล 2 ชุดที่ต้องตรงกันตลอดเวลา วันไหนลืมทำให้ตรง จะได้หน้าจอที่แสดงผิดโดยไม่มี error ให้จับ

เขียนแบบนี้แทน — สั้นกว่า ถูกต้องกว่า และไม่มีทางไม่ตรงกัน

const filtered = statusFilter === 'all'
  ? requests
  : requests.filter(r => r.status === statusFilter);

กฎที่ควรจำ — ข้อมูลที่คำนวณได้จาก state ที่มีอยู่แล้ว ให้คำนวณตอนวาดหน้าจอ อย่าเก็บซ้ำ

5.2 Dependency Array — บอก React ว่าเมื่อไรต้องทำใหม่

useEffect(() => {
  // โหลดข้อมูล
}, [scenario]);   ← ทำใหม่เมื่อ scenario เปลี่ยนเท่านั้น
🔵 ทายก่อนอ่านต่อ

ถ้าเราใส่ requests เข้าไปใน dependency array ของ Effect ที่โหลดข้อมูลแล้วเก็บผลลง requests — จะเกิดอะไรขึ้น

เฉลย

จะเกิดวงวนไม่รู้จบ Effect โหลดข้อมูลแล้วเซ็ต requests → requests เปลี่ยน → React เห็นว่า dependency เปลี่ยนจึงเรียก Effect อีกรอบ → โหลดอีก → เซ็ตอีก วนไปเรื่อย ๆ

อาการที่จะเห็น — หน้าจอค้าง พัดลมโน้ตบุ๊กดังขึ้น Console ขึ้นข้อความรัว ๆ และแท็บเบราว์เซอร์อาจไม่ตอบสนอง

วิธีแก้ — เอาออกจาก dependency array สิ่งที่ Effect ตัวนั้นเป็นคนเซ็ตเอง

🟡 หมายเหตุ · สิ่งที่คุณจะเห็นแล้วสงสัย

ระหว่างทำงาน คุณจะสังเกตว่า Effect ทำงาน 2 รอบ ทุกครั้งที่เปิดหน้า ทั้งที่เขียนไว้รอบเดียว

โค้ดคุณไม่ได้ผิด React ตั้งใจทำแบบนี้ในระหว่างพัฒนาเพื่อตรวจสอบบางอย่าง ตอนใช้งานจริงจะทำงานรอบเดียว

ตอนนี้ให้สังเกตไว้เฉย ๆ ก่อน แล้วเราจะคุยกันว่าทำไมในคาบ 5B — ถ้าคุณรู้สึกสงสัย นั่นคือสิ่งที่ต้องการพอดี

สรุปบทที่ 5
  • ถามว่า “อะไรทำให้งานนี้เริ่ม” แล้วจะรู้ว่าโค้ดควรอยู่ที่ไหน
  • Effect ใช้เชื่อมกับสิ่งที่อยู่นอก React เท่านั้น
  • ข้อมูลที่คำนวณได้จากของที่มีอยู่แล้ว ให้คำนวณตอนวาดหน้าจอ อย่าเก็บซ้ำ
  • อย่าใส่สิ่งที่ Effect เป็นคนเซ็ตเอง ลงใน dependency array

บทที่ 6

Data Lifecycle — เครื่องสถานะขนาดเล็ก

เวลาอ่าน ≈ 9 นาที

ใน Week 04 ข้อมูลอยู่ในตัวแปรตั้งแต่แรก จะใช้เมื่อไรก็หยิบได้ทันที แต่พอข้อมูลมาจากภายนอก มันไม่ได้มาทันที และอาจไม่มาเลยก็ได้

ช่วงเวลาระหว่างที่ยังไม่มีข้อมูล คือช่วงที่ผู้ใช้มองหน้าจอแล้วไม่รู้ว่าเกิดอะไรขึ้น การออกแบบช่วงนี้ให้ดีคือสิ่งที่แยกแอปที่ใช้งานได้ออกจากแอปที่น่าหงุดหงิด

สถานะความหมายผู้ใช้ควรเห็น
loadingยังไม่รู้ว่ามีข้อมูลหรือไม่ตัวบอกว่ากำลังโหลด
successได้ข้อมูลมาแล้วและมีรายการแผงสรุป ตัวกรอง และรายการคำร้อง
emptyได้ข้อมูลแล้ว แต่ไม่มีรายการข้อความชวนให้สร้างรายการแรก พร้อมปุ่มไปหน้าสร้าง
errorโหลดไม่สำเร็จข้อความที่คนทั่วไปเข้าใจ พร้อมปุ่มลองใหม่
🔵 ทายก่อนอ่านต่อ

ถ้าเราตรวจแค่ requests.length === 0 แล้วแสดงข้อความ “ยังไม่มีคำร้อง” — ผู้ใช้จะเห็นอะไรในวินาทีแรกที่เปิดหน้า

เฉลย

จะเห็นข้อความ “ยังไม่มีคำร้อง” แวบหนึ่ง ก่อนที่ข้อมูลจะขึ้น เพราะตอนเริ่มต้น requests ยังเป็น array ว่างอยู่

ผู้ใช้ที่มองไม่ทันอาจไม่รู้สึกอะไร แต่คนที่เห็นจะสับสน และถ้าเน็ตช้าข้อความนั้นจะค้างอยู่หลายวินาที

ต้องตรวจสองเงื่อนไขพร้อมกัน — loadState === 'success' && requests.length === 0

6.1 เราจะทดสอบสถานะ error ได้อย่างไร

ปัญหาที่แท้จริงของการทำ error state คือเราสั่งให้ระบบพังตามใจไม่ได้ จะรอให้เน็ตหลุดตอนตรวจงานก็ไม่ได้

LAB นี้จึงเตรียมทางลัดไว้ให้ในรูปของ URL พิเศษ

URLผลที่ได้
#/โหลดตามปกติ
#/?scenario=errorจำลองว่าโหลดไม่สำเร็จ
#/?scenario=emptyจำลองว่าไม่มีข้อมูล

ส่วนที่อยู่หลัง ? เรียกว่า query string — ต่างจาก :requestId ตรงที่ query string ไม่ใช่ส่วนหนึ่งของเส้นทาง แต่เป็นข้อมูลเสริมที่แนบไปกับเส้นทางนั้น อ่านค่าด้วย useSearchParams()

🟡 หมายเหตุ

สองสถานการณ์นี้เป็นเครื่องมือทดสอบของ LAB ไม่ใช่การหลอกผู้ใช้ว่าระบบพังจริง หน้าจอจึงต้องมีป้ายบอกไว้ด้วยว่ากำลังอยู่ในโหมดทดสอบ

เมื่อผู้ใช้กดปุ่มลองใหม่จากสถานะ error สิ่งแรกที่ต้องทำคือเอา scenario=error ออกจาก URL ไม่อย่างนั้นจะกดกี่ครั้งก็ error เหมือนเดิมตลอดไป

สรุปบทที่ 6
  • ข้อมูลจากภายนอกมาช้าและอาจไม่มาเลย จึงต้องมีสถานะรองรับให้ครบ
  • loading, success, empty, error และ retry — ห้ามขาดข้อใด
  • empty ต้องตรวจคู่กับ loadState ไม่ใช่ตรวจแค่จำนวนรายการ
  • ใช้ URL พิเศษเพื่อทดสอบ error และ empty ได้ตามต้องการ

บทที่ 7

Service Layer และเหตุผลที่ต้องมี

เวลาอ่าน ≈ 8 นาที

ถึงตรงนี้อาจมีคำถามค้างอยู่ว่า ทำไมต้องสร้างไฟล์ requestService.js เพิ่มอีกไฟล์ ในเมื่อ DashboardPage เรียก fetch() เองก็ได้

คำตอบไม่ได้อยู่ที่วันนี้ แต่อยู่ที่สิ่งที่จะเกิดขึ้นในอีกสองสัปดาห์

7.1 หน้าตาของ Service

// สิ่งที่ Page มองเห็น — แค่นี้
getRequests(options)        // ขอรายการคำร้องทั้งหมด
getRequestById(requestId)  // ขอคำร้องใบเดียวตามรหัส

// ที่จะเพิ่มในคาบ 5B
addRequest(input)
deleteRequest(requestId)
resetRequests()

DashboardPage ไม่รู้และไม่จำเป็นต้องรู้ว่าข้อมูลมาจากไหน มันรู้แค่ว่าเรียก getRequests() แล้วจะได้รายการกลับมา

7.2 ทำไมความไม่รู้นั้นถึงมีค่า

🟣 เก็บไว้สัปดาห์หน้า

ในคาบ 5B คุณจะทำให้ข้อมูลไม่หายตอน refresh ก่อนลงมือ ผมจะถามว่า “คิดว่า DashboardPage ต้องแก้กี่บรรทัด”

ลองเดาไว้ในใจตั้งแต่ตอนนี้ แล้วจดคำตอบไว้ — เราจะมาดูกันว่าตรงไหม

7.3 กติกาสองข้อที่ห้ามละเมิด

กติกาเหตุผล
fetch() อยู่ใน requestService.js เท่านั้นเมื่อวิธีดึงข้อมูลเปลี่ยน จะได้แก้ที่เดียว
หน้าและ component เรียก Service เท่านั้นไม่มีใครลัดเข้าไปหาข้อมูลเองได้

ทั้งสองข้อนี้ npm run check ตรวจจริง ถ้ามี fetch() โผล่ในไฟล์ Page งานจะไม่ผ่าน

7.4 อย่าลืมตรวจว่าโหลดสำเร็จ

จุดที่ผิดพลาดง่ายและหาสาเหตุยาก — fetch() ไม่โยน error เมื่อเซิร์ฟเวอร์ตอบ 404 มันถือว่าติดต่อสำเร็จแล้ว เพียงแต่ผลลัพธ์ที่ได้คือหน้า error

const response = await fetch(url);
if (!response.ok) throw new Error('ไม่สามารถโหลดข้อมูลตัวอย่างได้');
const data = await response.json();

ถ้าไม่ตรวจ response.ok แล้วเรียก .json() ต่อ คุณจะได้ error แปลก ๆ ว่าแปลง HTML เป็น JSON ไม่ได้ ซึ่งไม่ได้บอกอะไรเลยว่าปัญหาจริงคือหาไฟล์ไม่เจอ

สรุปบทที่ 7
  • Service คือกำแพงกั้นระหว่าง “อยากได้ข้อมูล” กับ “ได้มาอย่างไร”
  • แหล่งข้อมูลจะเปลี่ยน 3 ครั้งในเทอมนี้ แต่ UI ไม่ต้องแก้เลย
  • fetch() อยู่ในไฟล์เดียวเท่านั้น และ checker ตรวจข้อนี้
  • ต้องตรวจ response.ok ทุกครั้ง
